03 / SELECTED WORK

Things I've built recently.

Client systems. Open any case study for the problem, the constraint and the trade-off.

001

Dealer invoice intelligence

No API existed, so the pipeline drives OEM dealer portals with Playwright: it spots VINs in email, logs in, downloads the invoice and has Claude extract the data into Google Sheets. Heavy parsing runs server-side so Claude only sees raw text, which keeps costs down.

case study
Problem
Getting vehicle invoice data meant logging into manufacturer portals one VIN at a time.
Constraint
The OEM portals have no API.
Built
Playwright automation triggered by VINs in email, server-side parsing, and Claude extraction into Google Sheets.
Trade-off
Browser automation is more fragile than an API, but it was the only way in. Sending Claude parsed text instead of whole files keeps the cost per invoice down.
PlaywrightClaudeGoogle Sheets
002

AP invoice extraction

An Azure Logic App watches an accounts-payable inbox and sends each attached invoice to Claude for vendor, amount, dates and invoice number. Every step saves state and logs failures, invoices run one at a time to respect API limits, and a kill switch disables it all.

case study
Problem
Vendor invoices land in an accounts-payable inbox and had to be keyed in by hand.
Constraint
PDFs and images, sometimes several per email, and Claude API concurrency limits.
Built
A Logic App that handles each attachment, Claude extraction, a database record saved first with an error timestamp on failure, a manual-upload screen and a kill switch.
Trade-off
One-at-a-time processing is slower but avoids rate-limit failures. The manual-upload path repeats the Logic App steps; the next step is routing both through one API.
Azure Logic AppsClaudeTypeScript
003

LLM platform build-out

Built the integration and reliability layer for a tenant-messaging chatbot: an integration adapter framework, shared webhook handling, health checks, Sentry logging, tracing, rate limiting, test coverage and a refactored LLM tool layer.

case study
Problem
Every new property-management integration meant copying code.
Constraint
New integrations kept coming while the chatbot stayed live.
Built
An adapter base class, shared webhook handler, consolidated utilities, onboarding checklist, health checks, Sentry logging, tracing, rate limiting with backoff, ORM and integration tests, and a refactored LLM tool layer.
Trade-off
The platform stayed one service rather than splitting into microservices, because LLM inference, not infrastructure, was the bottleneck.
ArchitectureLLM systems
004

Secure exam browser

One Electron app replaced a plugin, a script and a remote-support install: process monitoring, VM detection, screen-capture blocking, OS lockdown and webcam streaming.

case study
Problem
Securing an exam took a browser plugin, a script and a remote-support install. It was clunky and could be worked around.
Constraint
Lock down the operating system on testers' own machines while streaming webcam and audio to a live proctor.
Built
One Electron app with process monitoring, VM and remote-control detection, screen-capture blocking, taskbar and task-switcher lockdown, server events and proctor controls.
Trade-off
Electron gives system-level access a browser can't, at the cost of shipping and updating a desktop app.
ElectronSecurity
005

Self-serve kiosk

Ordering kiosk proof of concept on Elo hardware for a restaurant chain's field test: menu, cart, register printing and data-warehouse batching.

case study
Problem
The chain wanted to test self-serve ordering before paying for a full kiosk rollout.
Constraint
Cheap enough to be a trial, polished enough to produce real research data.
Built
A kiosk app on Elo hardware with animations, menu, cart, register printing and transaction batching to a data warehouse.
Trade-off
Franchise management, admin dashboards and kitchen displays were left out to keep the trial low-cost, with room to add them later.
KioskData
